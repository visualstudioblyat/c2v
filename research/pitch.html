the thesis

Vitis HLS handles all of C++ — templates, dynamic memory, virtual functions, arbitrary pointers. That generality costs it everywhere. c2v only handles restricted Firedancer-style C — no heap, no recursion, no function pointers, fixed arrays, explicit dataflow. The restriction is the weapon.

Thorup's Theorem (1998): goto-free C programs have treewidth ≤ 6.
Scheduling on bounded-treewidth graphs is FPT (polynomial, not NP-hard). Vitis must handle arbitrary C++ with unbounded treewidth. We don't. This is provable, not heuristic.

the #1 gap: loop pipelining

This is the single feature that determines whether c2v competes with Vitis. We have the analysis (II computation, modulo scheduling). We need the emission.

pipelined loop (II=1):

  clock:  1    2    3    4    5    6    7    8
         +----+----+----+----+
  iter0  | LD | MUL| ADD| ST |
         +----+----+----+----+
              | LD | MUL| ADD| ST |       <-- new data every clock
                   | LD | MUL| ADD| ST |
                        | LD | MUL| ADD| ST |

  throughput: 1 result/cycle (after 4-cycle latency)

c2v today (FSM, no pipelining):

  clock:  1    2    3    4    5    6    7    8
         +----+----+----+----+
  iter0  | LD | MUL| ADD| ST |
         +----+----+----+----+
                              +----+----+----+----+
  iter1                       | LD | MUL| ADD| ST |

  throughput: 1 result/4 cycles

  speedup = (N * body) / ((N-1) * II + body)
  for N=1000, body=4, II=1: 4000/1003 = 3.99x

key equations

II ≥ max(ResII, RecII, MemII)
ResII = max ceil(N_type / available_units) · RecII = longest recurrence cycle ratio · MemII = ceil(accesses / ports)
Speedup = (N × body) / ((N-1) × II + body)
For N=1000, body=4, II=1: 4000/1003 ≈ 3.99x
tw(G) ≤ 6 for goto-free C (Thorup) → scheduling ∈ FPT
Optimal scheduling for restricted C is polynomial-time. Vitis handles general C++ where treewidth is unbounded — stuck with heuristics.
W/D = parallelism bound (Dilworth) · H = Σ log₂(width) (Shannon)
